# VolSync Kopia → Kopiur (staged, not cut over)

This directory prepares the 14 existing `ReplicationSource`s for Kopiur 0.10.16. It **does not switch backups**: `kopiur-system-migration` is suspended, and each new `SnapshotSchedule` is suspended. The original VolSync sources and `KopiaMaintenance/rsync-net` remain active. The chart is pinned, installs its CRDs, and can run alongside VolSync without creating any Kopiur repository until the migration gate is opened.

## Blockers before opening the migration gate

1. rsync.net currently authenticates with `SFTP_PASSWORD`. Kopiur's SFTP backend accepts **SSH keys only**. Create a dedicated unencrypted (no passphrase) SSH keypair, authorize its public key on the existing rsync.net account, test SFTP access to the *existing* `/data1/home/<user>/volsync` path, and save only its private half in Bitwarden as `rsyncNetKopiurSshPrivateKey`. Never commit the key, password, endpoint, username, rendered Flux output, or a plaintext Secret to this public repository. Verify `rsyncNetKnownHosts` matches the host's current SSH host key (do not trust blindly).
2. Check `ExternalSecret/kopiur-coordinates` in `flux-system` is synced. Flux reads this Secret to substitute `${RSYNC_NET_HOST}` and `${RSYNC_NET_USER}` into the `ClusterRepository` manifest. The SFTP credentials are fanned out by `ClusterExternalSecret/kopiur-sftp-creds` to the existing five application namespaces and `volsync-system` **only after** the migration Kustomization is resumed. Existing `volsync-kopia` remains untouched and supplies the Kopia encryption password.
3. Review the generated identities (`<replicationsource-name>@<namespace>:/data`) against actual Kopia snapshot identities. The converter mapped all 14 sources but cannot map `accessModes` (it derives staging access modes from the PVC) or `cacheAccessModes` (Kopiur's cache has no such field). Verify each PVC can be snapshotted with the `ceph-block` class. `seeer-config-v2` is intentionally retained because it matches the live Seerr PVC.
4. Check the rsync.net repository can handle concurrent access and the existing Kopia history is visible. Existing backup health/maintenance should be reviewed first; a stalled maintenance or index-blobs problem does not disappear merely by changing controllers.

## Cutover (subsequent changes, not this PR)

- Pilot `media/autobrr-kopia` first. After SSH key and coordinates are synced, remove `spec.suspend: true` **only** from the `kopiur-system-migration` Flux Kustomization. All schedules remain suspended and default Kopiur maintenance is disabled. Verify the ClusterRepository is Ready and old snapshots appear as `origin: discovered` under the pinned identity. Do **not** turn on both operators' schedules for the same source.
- Suspend the pilot VolSync `ReplicationSource`, then run a manual Kopiur snapshot (`kubectl kopiur snapshot now --policy autobrr-kopia -n media --wait`) and verify it appears under the same identity. Restore an existing and a new snapshot into separate scratch PVCs and inspect their contents before enabling the Kopiur schedule. Keep the VolSync source definition available for rollback until retention coverage is proved.
- Migrate the other sources in batches: suspend each old source, test a Kopiur backup and restore, then enable that source's `SnapshotSchedule` (remove its `suspend: true`), review retention/history, and only later remove its old `ReplicationSource`. Do not trust a created snapshot alone as a successful backup.
- Kopiur and the fork **must not** run maintenance for the same repository. After the adopted repository is Ready, retire `KopiaMaintenance/rsync-net` and enable maintenance on the ClusterRepository in the **same coordinated cutover** (Kopiur default quick every 6h/full daily). Keep VolSync installed until all sources are migrated and any restore destinations are reviewed. The live `infra/unifi-kopia` one-shot `ReplicationDestination` (not in Git) is deliberately not pruned by this PR.
- Roll back a failed pilot by re-suspending its Kopiur schedule, restoring the original VolSync `ReplicationSource` schedule, and leaving the repository/credentials intact. Do not delete the shared repository or its original Secret.

The manifests were generated with `kubectl-kopiur 0.10.16 migrate volsync -f <each source> --repository volsync-kopia --repository-kind cluster-repository`, then their schedules were explicitly suspended. Installation/migration references: https://kopiur.home-operations.com/install/ and https://kopiur.home-operations.com/cli/migrate-volsync/.
